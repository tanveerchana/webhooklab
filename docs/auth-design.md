# Account authentication and company workspaces

Each application offers an isolated personal demo and a separate account mode. Demo bearer workspaces remain unchanged. New email/password accounts use the existing Supabase Auth project and its confirmation, SMTP, password, and rate-limit settings. No auth settings are changed, no administrator key is used, and tests do not send real emails.

## Implementation plan and boundaries

1. Add server-only email/password exchange, provider-verified session lookup, refresh, and sign-out with app-specific protected cookies.
2. Add dedicated account workspace, membership, invitation, and backend-credential tables in a new private schema; expose checked RPC gateways only.
3. Route account workspace reads and mutations separately from legacy demo tokens; enforce permissions in both Node and SQL.
4. Add owner-managed teams and a separate, scoped WebhookLab ingestion capability.
5. Verify authentication and authorization with injected-provider tests, rollback-only database assertions, formatting, TypeScript, app builds, and an independent security review.

The implementation is installed in the hosted database. Hosted rollback authorization assertions pass; email delivery and a complete provider account browser journey remain unverified. Existing production and demo tables are not changed by account-schema.sql.

## Browser and API contract

- `GET /api/auth?action=session` returns `{user:{id,email}|null}`.
- `POST /api/auth` accepts JSON `{action:'login'|'signup'|'logout',email?,password?}`. Signup returns `confirmationRequired`. Signup requires 12–128 password characters; existing account sign-in permits 1–128. Confirmation-required signup creates no browser session; the user follows the provider email and returns to sign in. The provider's existing confirmation redirect configuration is preserved.
- Cookies are app-specific `__Host-portfolio_<app>_access` and `__Host-portfolio_<app>_refresh`, host-only, `Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax`. Access expires with the provider's bounded lifetime; refresh cookie lasts seven days. Account access/refresh tokens and passwords are never returned to browser JavaScript or logged. The browser never stores these values in localStorage.
- Every account request calls `GET /auth/v1/user`; decoded JWT claims and editable metadata do not establish identity. Expired access is refreshed server-side and the new access token is verified with another `/user` call. Unavailable provider responses return a generic 503. Invalid sessions clear cookies. Logout revokes the current provider session/refresh credentials with local scope and always clears both browser cookies; provider failures return an explicit error rather than claiming remote revocation succeeded.
- Cookie-authenticated mutations require an exact same-origin `Origin`, `application/json`, and no `Sec-Fetch-Site: cross-site`. Host is taken from the request's Host header, HTTPS in deployment, or HTTP for localhost development. No wildcard CORS is enabled. Login and signup have the same origin protection.
- Account workspace requests require `X-Workspace-Mode: account` and `X-Workspace-Id: <UUID>`. Account mode never falls back to a demo bearer token. Legacy demo mode accepts `X-Workspace-Mode: demo` or its existing omitted-mode behavior.
- `GET /api/team`, optionally with `X-Workspace-Id`, returns `{workspaces:[{id,name,role}],workspaceId?,members?,pendingInvitations?}`. Members use `{userId,email,role}`. Pending invitations are owner-visible `{id,email,role}`.
- `POST /api/team` accepts `{action:'create',name}`, `{action:'invite',workspaceId,email,role}`, `{action:'role',workspaceId,userId,role}`, or `{action:'remove',workspaceId,userId}`. Create uses the application's synthetic sample seed. Team actions do not send email; pending invitations are matched when the invited verified account opens its workspace list. The UI should explain that the owner shares the app URL separately.

## Database trust model

`account-schema.sql` creates only a new `portfolio_account_private` schema with isolated `portfolio_account_*` tables and functions, plus public `portfolio_account_*` SECURITY INVOKER wrappers. The private tables have RLS enabled/forced, no permissive policies, and no SELECT/INSERT/UPDATE/DELETE grants for anon/authenticated. Direct table reads cannot bypass viewer secret redaction. Public wrapper EXECUTE is revoked from PUBLIC and explicitly granted only to required roles.

The narrow private gateway functions intentionally use SECURITY DEFINER and empty search_path. They explicitly check `auth.uid()`, current membership, app scope, verified `auth.users.email` with non-null `email_confirmed_at`, and the requested operation. They are the legitimate privileged data gateway. Private helpers are not executable by API roles; only checked gateways are granted. Never expose this private schema through the Supabase Data API, expose private tables via views, grant table access to API roles, or add service-role credentials.

Every full-state CAS write and seeded workspace creation additionally requires an independent app-bound backend credential. This prevents a user possessing their own valid JWT from bypassing Node domain validation by calling a raw-state RPC with a forged command label. Node uses the verified user's access token and `PORTFOLIO_BACKEND_KEY`; the database checks both. Each application's key is a separate random 32-byte lowercase hexadecimal value. Store only SHA-256(key) in `portfolio_account_private.portfolio_account_backend_credentials(app,key_hash)`. Allowed app identifiers are `webhooklab`, `fieldpilot`, and `payroute`. Never expose the raw key to frontend code, responses, logs, or source control. RPC body logging must redact `p_backend_key`, `p_integration_key`, and Authorization headers.

Workspace creation assigns the creator owner in SQL, ignoring client role fields. Invitations and role changes can grant only editor/viewer, plus FieldPilot staff; owner is never a caller-selectable grant. Owner self-removal and owner-role changes/removal are denied, preserving the last owner. Expired pending invitations are pruned before invitation quota checks. Workspaces are limited to 10 created per user/app and teams to 100 active members/pending invitations. Workspace state is object JSON bounded to 512 KB, with an integer CAS revision. Account workspaces do not expire with demo tokens.

CAS locks the workspace before checking current membership, then returns a stale-revision result before comparing changed sections. Team changes and key rotation use the same workspace lock. A revoked membership cannot use an earlier cached role to commit a new change. Node reloads and clones state for at most five mutation attempts.

| Role   | FieldPilot                                               | PayRoute                                               | WebhookLab                                                           |
| ------ | -------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| Owner  | Business commands, team management                       | All simulation/configuration commands, team management | Capture/replay/clock, reset/secret/settings, team and ingestion keys |
| Editor | All business commands                                    | Simulate and reconcile                                 | Sample/capture/replay/advance-clock                                  |
| Staff  | Move one job through scheduled → in_progress → completed | Unavailable                                            | Unavailable                                                          |
| Viewer | Read company sample data                                 | Read company sample data                               | Read events; signing secret is omitted in SQL and Node               |

SQL independently checks the app/command allowlist and role. Staff writes may change only jobs/activity, preserve all non-status job fields, and move exactly one job one legal step. PayRoute editor writes cannot change provider configuration, and reconciliation cannot rewrite payments. WebhookLab editor writes may change events or clock as appropriate, preserving the signing secret and settings. Node domain reducers enforce complete business validation. Owners/editors may see WebhookLab's HMAC signing secret as event producers; viewers cannot obtain it.

## Webhook integration credentials

`GET /api/integrations` with account cookies and workspace header returns `{workspaceId,configured}`. Owner-only JSON POST `{action:'rotate'|'revoke',workspaceId}` rotates or revokes a dedicated ingestion key. Rotation returns `{workspaceId,configured:true,integrationKey}` exactly once; only its hash is stored. It has prefix `whk_ingest_` plus 64 random lowercase hexadecimal characters. Integration keys are separate from account sessions and the HMAC signing secret.

Account `/api/ingest` accepts the ingestion key in Bearer authorization plus `X-Workspace-Id`, and the HMAC signature over the exact payload. Its Node backend performs state read/CAS using BOTH the scoped ingestion key and WebhookLab's independent backend credential. An external integration key alone cannot invoke a raw-state read RPC and retrieve the signing secret. The integration CAS permits events only; signing secret, clock, settings, and memberships are immutable. The HTTP ingestion endpoint returns a receipt only, never workspace state. Revocation/rotation immediately invalidates the old ingestion key at the database gateway. Existing demo ingestion keeps its legacy bearer flow.

## Installation and verification

Preflight pgcrypto's real schema and API-role schema usage as described in demo-persistence.md. The account migration checks `extensions.digest(text,text)` and usage. It deliberately fails if the dedicated schema already exists so older versions require explicit review. Apply account-schema.sql once; do not alter any existing Auth settings. Set server-only `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and a distinct `PORTFOLIO_BACKEND_KEY` for each deployment. Register the matching hash per app using an administrator connection; never put raw keys into a committed SQL file. Keep `portfolio_account_private` out of exposed Data API schemas.

Run shared `npm test` and strict TypeScript; run each app's tests/typecheck/build/format checks. `tests/account-rls.sql` is a complete BEGIN/ROLLBACK transaction requiring two distinct existing verified synthetic test users, provided via `portfolio_test.user_a` and `portfolio_test.user_b` session settings. It creates only temporary-in-transaction account fixtures, swaps credential hashes inside the transaction, and rolls everything back; it never inserts/updates auth.users or changes Auth settings, and sends no emails. It checks cross-workspace/app isolation, viewer DB redaction/write denial, private table access denial, forged backend credentials, owner-role injection/self-removal, staff financial isolation and transitions, stale CAS, invitations, membership removal, and two-factor ingestion capability scope. A real provider/REST smoke test should additionally confirm cookie issuance, refresh, password failure/limits, existing email confirmation delivery configuration, and PostgREST request JWT propagation using synthetic accounts. Do not describe injected-fetch or local database tests as hosted/provider verification.

An independent review examined the auth/cookie/origin boundary, backend credential guard, grants, verified-email matching, role restrictions, membership races, ingestion scope, and expiry/quota lifecycle. Findings corrected before deployment: raw-state CAS now requires backend credentials; expired invitations no longer exhaust quota; CAS checks stale revisions before section comparisons; login continues supporting existing provider passwords.
